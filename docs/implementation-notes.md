# Implementation notes: deliberate deviations from the TRD

Where the build departs from `docs/TRD.md` on purpose, the reason is recorded here. A deviation that changes behaviour the owner cares about goes in `docs/decisions.md` instead.

| Frontend kit (§18.1) | shadcn/ui, react-hook-form, vite-plugin-pwa | Plain Tailwind components and native forms; the PWA arrives with offline roll call (ticket 26) | Bundle budget (§18.3); nothing in the early tickets needs them. |

| Offline queue (handoff §9.20, §10.4, WP-UI-07) | Assignment submissions, quiz answers, attendance overrides and grade edits queue in IndexedDB with their Idempotency-Key | `apps/web/src/offline/` queues assignment submissions (WP-UI-07), roll-call marks and attendance overrides (WP-UI-09), and quiz answers (WP-UI-11). Roll call is a versioned write (`If-Match`): a queued batch carries the version it was made against and, if someone saved first (412), reads the latest and sends again on top, up to three times (`sendStep`), which is what the old page did. Marks the old page left in `localStorage` are taken over once on opening roll call. Quiz answers moved to the queue in WP-UI-11 (group `quiz:<attemptId>`): answers are gathered for 800 ms after a change, as before, and queued as one `PATCH /quiz-attempts/:id` with a rising `seq`. A new batch is folded into the attempt's newest save that hasn't started sending (`enqueue(work, merge)`, newer answer per question and newer `seq`), so answers made offline go back as one request within the deadline's grace, as the old page's single merged save did; an item being sent is never changed, and the queue re-reads each item before sending it. A merged item takes the newer batch's Idempotency-Key (its body is new). While answers wait, the page itself retries every 3 s, as the old page did, and says when they still haven't gone. Queue-wide (WP-UI-11 review): a server error (5xx, 429, a key in progress) holds back only that item's group, so one screen's stuck work never blocks another's, while no answer at all (offline) stops the flush; a flush runs again for work queued while it was sending; and when IndexedDB is refused, work is kept in localStorage (surviving a reload, as the old per-screen queues did), then memory. The server ignores a stale `seq` and the queue sends oldest first, so the latest answer to each question wins. Batches are also queued when the page is hidden or left. At the deadline or on Submit the page queues what it has, flushes, and submits only once the attempt's group is empty, trying again every 3 s while offline (the server accepts answers for 30 s after the deadline). A save refused with `ATTEMPT_EXPIRED` is dropped silently as before; any other refusal is dropped and said in a Banner (the old page retried it forever). Answers the old page left in `localStorage` are taken over once on opening the attempt. Grade edits are not queued: each cell is guarded by its own version, and replaying a score over someone else's change needs a design (show both? ask?) before it is safe. Offline, a grade edit says so and keeps the typed value. File attachments need a connection: the bytes go straight to storage through a presigned URL, so they can't wait in the queue. | Moves each screen's queue with its redesign rather than all at once. |
