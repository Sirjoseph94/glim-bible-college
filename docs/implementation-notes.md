# Implementation notes: deliberate deviations from the TRD

Where the build departs from `docs/TRD.md` on purpose, the reason is recorded here. A deviation that changes behaviour the owner cares about goes in `docs/decisions.md` instead.

| Area | TRD says | Built | Why |
|---|---|---|---|
| API client (§18.1) | Typed client generated from OpenAPI | `apps/web/src/api/client.ts` typed directly from the endpoint contracts in `packages/contracts` (types only) | The contracts are the source of the OpenAPI document too, so the types are identical, with no generation step and no Zod in the browser bundle. |
| Frontend kit (§18.1) | shadcn/ui, react-hook-form, vite-plugin-pwa | Plain Tailwind components and native forms; the PWA arrives with offline roll call (ticket 26) | Bundle budget (§18.3); nothing in the early tickets needs them. |
| OpenAPI (§4.4) | Zod → OpenAPI via the Nest ecosystem | `apps/api/src/openapi.ts` builds OpenAPI 3.1 from the contracts with `z.toJSONSchema` | `nestjs-zod` and `@nestjs/swagger` don't support NestJS 12. |
| `Db.withTx(ctx, fn)` (§5.2) | Takes a request context | `withTx(fn)`, plus `withTxResult(fn)`, which rolls back when a use case returns an expected failure (§5.8) | The context (actor, request id) travels as an explicit `AuditActor` argument. |
| Invite/reset tokens (§8.1) | Single-use, stored as SHA-256; no table defined | `auth_tokens` (owner: identity) | The DDL names no home for them. |
| Lockout (§8.1, Appendix D) | Lockout plus uniform errors | A locked account answers exactly like a wrong password; `ACCOUNT_LOCKED` is unused | Distinct lockout replies would reveal which emails have accounts. |
| Applicant sessions (§8.3) | Idle 24 h for applicants | Idle 24 h, absolute 12 h for everyone | As written; the absolute limit still applies. |
| Client IP (§5.4) | Rate limits per IP | `CLIENT_IP_HEADER` (App Platform: `do-connecting-ip`); `X-Forwarded-For` is never trusted | A client can forge `X-Forwarded-For`. |
| Same-origin writes (§19.1) | Check `Origin`/`Sec-Fetch-Site` | A write must carry one of them, and it must match | Public writes (login, reset, invite) have no CSRF token. |
| Job retention (§17.1) | Archive after 7 days, delete after 30 | `deleteAfterSeconds` 30 days | pg-boss 12 has no archive table. |
| `meeting-tick` (§17.2) | A cron with no queue in §17.1 | Queue `meeting.tick` | pg-boss schedules jobs onto a queue. Cron is registered only for queues that have a handler. |
| Mail (§4.4) | `@sendgrid/mail` | SendGrid v3 REST over `fetch` | One request type; no SDK needed. |
| Policies (§6.2) | Eight policy types | v1 edits ATTENDANCE, JOIN_WINDOW, RECORDING, NOTIFICATION, ADMISSIONS and GRADING_DEFAULTS; schemas and defaults in `packages/contracts/src/policies.ts` | GOOGLE_MEET and RETENTION belong to the integration slice. A type with no saved version uses its defaults (version 0). |
| Time library (§4.4) | `luxon` | `Intl.DateTimeFormat` in `packages/shared/src/time.ts` (browser-safe subpath `@glim/shared/time`) | Keeps the browser bundle small. Server-side recurrence (ticket 24) brings its own library. |
| Images (§22.4) | `Dockerfile.api` and `Dockerfile.worker` | One `docker/Dockerfile`; the components differ by run command. It includes `pg_dump` 18 | Simpler to build and scan. The worker's backup and any component can use any tool in it. |
| Runtime (§22.4) | Compiled output | `tsx` runs the TypeScript sources in production, as in development | Workspace packages export their sources, and file-relative assets (migrations, the breached-password list) resolve the same in dev, tests and production. Startup compiles in a couple of seconds. |
| Logical backup encryption (§22.7) | `age` CLI | `age-encryption` (the reference JS implementation); decrypt with the `age` CLI | No extra binary in the image; same file format. |
| Starting an application (§7.3, §20) | Applicant endpoints use `admissions:application:own-*` | `POST /applications` and `GET /applications/mine` need only a session; `GET`/`PATCH /applications/:id` use `own-edit` on the `application` resource | A self-registered user isn't an Applicant until they own an application, so no permission can grant the first one. The service limits each user to their own drafts. |
| Spiritual background to the applicant (§10.5) | Returned only to holders of `read-sensitive` | The applicant also gets their own section 5 answers back, on their own application only | They must see what they typed to edit the draft. Staff access stays as the TRD says (ticket 15). |
| Texts shown (§10.2) | "The version shown is stored with the application" | `applications.admissions_policy_version`, set when the applicant declares or consents | The DDL names no column for it. |
| Draft autosave (§10.3, INV-11) | Every transition is audited | Starting an application is audited and recorded in `application_events`; autosaves are not | Autosave runs every few seconds and changes no status; auditing it would flood the log. |
| File permissions (§7.3, §20) | Files are "own/authz" | File endpoints need only a session. `FilesService` lets the owner act on their file, and lets others download only with the purpose's read permission (passport photos: `admissions:application:read`); anyone else gets a 404 | The catalogue has no file permissions; access follows from the purpose. Upload purposes join with their features (`PASSPORT_PHOTO`; `IMPORT`, readable with `identity:import:run`). |
| Idempotency (§5.4) | Insert the `IN_PROGRESS` key in the operation's own transaction | `IdempotencyInterceptor` claims the key in a short transaction of its own, runs the operation, then stores the response (or forgets the claim if the operation failed). A claim left `IN_PROGRESS` for over 2 minutes counts as abandoned and may be claimed again | Keeps every use case free of idempotency plumbing. A crash between the operation and storing its response is covered by the abandoned-claim rule, and each idempotent operation also checks its own state (e.g. only a DRAFT can be submitted). |
| Notifications (§15.1) | `notifications` + `notification_preferences`, digest, quiet hours | `notifications` and `notify.send` only, for critical kinds (the application receipt so far) | Preferences, the digest and quiet hours apply to non-critical kinds, which arrive with their features. |
| Officer view of drafts (§10.3) | The queue lists applications | The queue and detail show only submitted applications; a draft returns 404 to staff | A draft is the applicant's unfinished work; it has no reference number to review against. |
| Interview and other notes (§10.3) | "Recorded as a note" | Notes are `application_events` rows whose status doesn't change (`from_status = to_status`, `note` set). The applicant's timeline leaves them out | Uses the TRD's `note` column, with no new table. |
| Acceptance details (§10.4) | Enrollment fields listed, no dates or codes given | `started_on` is the entry session's start date. The cohort code is `{programme}-{intake}` (e.g. `DIP-2027`). The Matric year is the intake's year. A programme with no ACTIVE curriculum refuses acceptance (409) and asks the applicant to contact Admissions | Fills the gaps the TRD leaves. |
| Cohorts table (§6.3) | Owner: academic | Defined in `schema/cohorts.ts` rather than `schema/academic.ts` | It references both academic and admissions tables, and one file would create an import cycle. Ownership is unchanged. |
| Referral codes (§10.6) | Created on acceptance, import or staff creation | Also when an existing user becomes a Lecturer or is given a staff role. Users created before this change get one on their next such event; there is no backfill | No production data exists yet, so no backfill is needed. |
| Admissions report (§10.6) | Counts by status, programme, study mode, country and `heard_via` | Counts submitted applications, plus a separate count of drafts in progress | Drafts are the applicant's private work (see the officer-view row above). |
| CSV downloads (§10.6, §10.5) | "CSV or JSON" | `?format=csv` returns a `text/csv` attachment through the same endpoint. Cells starting with `=`, `+`, `-`, `@` are prefixed with `'` | Avoids spreadsheet formula injection from applicant-entered text. |
| Purge scope (§10.5) | Deletes the application, its events and its photo file | Also deletes the in-app notifications about the application (they hold the applicant's name and reference) | Same retention rule as the application itself. |
| Import kinds (§15.2) | `STUDENTS`, `LECTURERS`, `COURSE_ENROLLMENTS`, `COURSE_RESULTS` | The first three; `COURSE_RESULTS` arrives with legacy results (ticket 39). The table's check constraint already allows it | Legacy results need the results module. |
| Import templates (§15.2) | `/imports/templates/:kind.csv` | `GET /imports/templates/:kind` returns a `text/csv` attachment | Route params can't carry a suffix cleanly; the download is still a CSV file. |
| Import dry run (§15.2) | Validate every row | Each batch is applied for real and then rolled back, so the dry run's created/updated/unchanged counts match what a commit would do. A commit needs a completed dry run of the same file and kind, and an unchanged hash (`IMPORT_FILE_CHANGED`) | Catches database-level conflicts (e.g. a Matric Number already used) before anything is written. |
| Import natural keys (§15.2) | `email`, `matric_number`, `staff_code`, `(matric_number, offering)` | Students by Matric Number (account by email). Lecturers by staff code, then by the account's email. Course enrollments by Matric Number + course code + session + semester + section (default `01`) | An offering has no single code a CSV can carry. |
| Import invites (§15.2) | "Creates an invite", rate-capped | Each new user gets a referral code and an `identity.invite` job, spread at 20 a second with `startAfter`. A user who has already accepted is skipped | Avoids a burst of mail on a large import. |
| Import resume (§15.2) | Resumable by row offset | `rows_done` is saved with each committed batch; a retried job carries on from there. The error CSV of a resumed run lists only the rows checked after the resume | Earlier rows' errors are in the dry run's error CSV, which checks the same file. |
| Semester close (§9.1) | Offerings become COMPLETED; ENROLLED course enrollments become COMPLETED; `academic.semester.closed` enqueues `results.compute-semester` | PUBLISHED and ACTIVE offerings complete; DRAFT and CANCELLED ones are left alone. Enrollment completes course enrollments through a step it registers with `CalendarService.onSemesterClose`, inside the closing transaction. Nothing subscribes to `academic.semester.closed` yet; results computation subscribes with ticket 38 | Each module writes only its own tables (§4.3), and enrollment already depends on academic. A queued job with no handler would only pile up. |
| Progression (§9.1, D-03) | Every ACTIVE Diploma enrollment at Year 1 that started in an earlier session advances | Any programme with a second Level, Level 1 → 2 only, via the `academic.progression` job on `academic.session.activated`; skipped unless the session is ACTIVE | Only Level 1 rows move, so a rerun can't advance anyone twice. |
| Conflict details (§9.5) | `LECTURER_SCHEDULE_CONFLICT` "with the conflicting meetings" | The error envelope gains an optional `conflicts: [{meetingId, title, scheduledStart, scheduledEnd}]`, also on `ROOM_CONFLICT` | The envelope had no field for them. |
| Class Meeting provider columns (§6.4) | `provider` and `provider_status` NOT NULL with defaults; `host_account_id` references `provider_host_accounts` | Both nullable and NULL in v1; `host_account_id` has no foreign key yet | v1 spec: meetings are created ready, with no provider. The host-accounts table belongs to the integration slice. |
| Online link in reads (v1 spec) | Students get the link from `/join` | Meeting reads carry `hasOnlineLink` for everyone and `onlineLink` only for people with `meeting:class-meeting:manage` on the offering | So the link only reaches students near class time (spec story 85). |
| Conflict override (§9.5) | "An Academic Admin may resubmit with `overrideConflicts=true` + reason" | Only holders of the ACADEMIC_ADMIN role; anyone else gets 403 | As written; System Admins don't book classes. |
| Lecturer slots on assignment (§9.4) | Adding an assignment updates slots for future meetings | A Lecturer busy at one of the offering's future meetings can't be assigned (`LECTURER_SCHEDULE_CONFLICT`, with the meetings) | Writing the slot would break `no_lecturer_overlap`; the admin resolves the clash first. |
| Single Class Meetings (§11.6) | Create with conflict checks | Must start in the future and last 5–600 minutes (the series limits). `PATCH` changes title, description, online link and recording mode; times and the Room change by reschedule (ticket 24) | Keeps every time change behind the conflict checks. |
| `GET /me/schedule` (§16) | "My schedule" | The next 14 days by default (`from`/`to` override). Students see meetings of offerings they're ENROLLED on that are PUBLISHED or ACTIVE; Lecturers see their assigned offerings | The catalogue gives no window. |
| Series recurrence (§11.9, §4.4) | `rrule` expanded with luxon | Weekly rules only (`FREQ=WEEKLY;INTERVAL;BYDAY[;UNTIL]`), expanded over calendar dates in `modules/scheduling/weekly.ts`; each date's time is read in the institution's zone with `zonedToInstant` | v1 series are weekly (spec story 59); no date library needed, and daylight-saving changes keep the wall-clock time. |
| Series horizon (§11.9, §17.1) | "8-week horizon, extended daily"; no queue named | Queue `class-meeting.series-extend`, cron 00:15 Lagos. An occurrence that would clash is skipped and audited (`meeting.series.occurrence-skipped`); an override given at creation isn't kept for later occurrences | A job has no one to choose another time. The series table has no column for an override. |
| Series edits (§11.9) | `THIS_ONLY` and `ALL_FUTURE` | `PATCH /class-meetings/:id` takes `scope`. THIS_ONLY marks the occurrence `series_exception`. ALL_FUTURE changes this and the later upcoming occurrences except those changed on their own, and updates the series; it can move the time of day but not the date | Moving a series to another weekday is cleaner as cancel-the-rest plus a new series. |
| Cancel (§11.9) | Cancel one meeting | `POST /class-meetings/:id/cancel` also takes `scope`; ALL_FUTURE cancels the series' later upcoming meetings and ends the series. Cancelling deletes the meetings' Lecturer slots | `no_lecturer_overlap` doesn't look at meeting state. |
| Reschedule notices (§11.9) | Notify enrollees | One in-app notification and one email (critical) per ENROLLED student per change, however many meetings it covers, with times in the student's zone and Lagos alongside | Avoids a flood of email for an ALL_FUTURE change. |
