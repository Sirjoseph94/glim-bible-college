## Agent Brief

**Category:** enhancement
**Summary:** `ClassMeeting` carries the cancellation reason, and the web client exposes `Retry-After` so the card can count down.

**Current behavior:**
- `POST /class-meetings/:id/cancel` takes a reason and stores it (`class_meetings.cancel_reason`), and the cancel form tells the Lecturer "Students will see that it is cancelled, with your reason". But no read returns the reason, so the card shows only a struck-through title.
- `PROVIDER_NOT_READY` responses carry a `Retry-After` header (30 s), but the web `ApiError` keeps only the body, so the card says "Try again in a few seconds" with no countdown.

**Desired behavior:**
- `classMeetingSchema` adds `cancelReason: string | null`. It is set only when the meeting is `CANCELLED`, and shown to everyone who can see the meeting, matching what the cancel form promises.
- The cancelled card shows the reason under the title, as a quiet line.
- `ApiError` exposes `retryAfterSeconds: number | null`, parsed from `Retry-After` (seconds, or an HTTP date). It is null when the header is absent or invalid.
- On `PROVIDER_NOT_READY`, the card's warning text counts down ("Try again in 28 s"), and the Join button is disabled until the count reaches zero. Without `Retry-After` it behaves as now.

**Key interfaces:**
- `classMeetingSchema.cancelReason`
- `ApiError.retryAfterSeconds`

**Acceptance criteria:**
- [ ] A cancelled meeting's reason comes back in the offering's list and in `/me/schedule`; it is `null` for any other state (integration test).
- [ ] `ApiError` parses `Retry-After` in both its seconds and date forms, and returns null when it is missing (unit test).
- [ ] The card shows the reason when cancelled, and the countdown with Join disabled after `PROVIDER_NOT_READY` (component tests).
- [ ] Typecheck, lint, unit, integration and budget checks pass.

**Out of scope:**
- Telling students the reason by email. That's the notification template, a separate change.
